# 債権管理の業務フロー

freee債権管理 Public APIを、複数のAPI操作を組み合わせて安全に使うためのガイド。

一覧取得、詳細取得など、単一のAPI呼び出しで完結する操作方法はこのレシピに重複して書かない。各エンドポイントの必須項目、型、制約、絞り込み条件は、正式OpenAPIから自動生成される次のリファレンスを参照する。

- `references/receivable-management-allocations.md` - 消込（消込、消込結果、取引反映、取引反映の取消、解除）
- `references/receivable-management-misc.md` - 請求、請求明細、入金、当月の利用状況（タグごとの行範囲は `references/INDEX.md` を参照）

このレシピで扱うのは次の業務フローに限る。

- 請求と入金を特定し、金額を確かめてから消込する
- 消込結果を freee会計 に取引反映し、非同期の結果を確認する
- 取引反映の取消と消込の解除を区別し、誤った取り消しを防ぐ

## 共通の事前確認

1. `freee_server_info` でサーバーバージョンを確認する
2. `freee_get_current_company` で対象事業所と `company_id` を確認する
3. リファレンスで、使用するメソッドの必須項目・型・制約を確認する

`company_id` は現在の事業所と一致させる。GETとDELETEでは `query`、POSTでは `body` に指定する。対象事業所を変更する場合は、先に `freee_set_current_company` で切り替える。

請求・入金・消込結果のIDは ULID 形式の文字列で、freee会計 の取引IDとは別物である。IDは一覧や詳細の取得結果から使い、推測しない。

## 業務フロー1: 請求と入金を特定して消込する

消込はユーザーの依頼内容（取引先、請求書番号、入金日、金額など）から対象を特定し、金額を確かめてから登録する。

1. 請求一覧で対象の請求を探す。取引先や請求書番号が分かっている場合は絞り込み条件に使う。取引先名は返らないため、名前で探す場合は先に freee会計 の取引先APIで `partner_id` を確認する
2. 入金一覧で対象の入金を探す。消込済みの入金を除くため、消込状況で絞り込む
3. 候補が複数ある、または一致するものが無い場合は、候補をユーザーに示して対象を確定してもらう。金額が近いだけで対象を決めない
4. 請求取得・入金取得で最新の請求残額（`due_amount`）と入金残額（`unallocated_amount`）を確認する
5. 請求と入金の差額を計算する。差額がある場合は、振込手数料などの差額調整として扱うか、勘定科目と金額をユーザーに確認する。差額調整の符号と金額の条件はリファレンスに従う
6. 多数の入金を消込する場合は、当月の利用状況を取得し、上限件数を超えると従量課金の対象になることをユーザーに伝える
7. 対象事業所、請求（請求書番号・取引先・請求残額）、入金（入金日・金額）、差額調整の内容を示し、ユーザーの確認を得てから消込を登録する
8. 返された消込結果IDで消込結果を取得し、status が allocated（取引反映待ち）になっていること、内訳が意図どおりであることを確認する

消込の結果が分からない場合（タイムアウトなど）は、すぐに再登録せず、入金取得で入金残額が 0 になっているかを先に確認する。

消込しただけでは freee会計 には計上されない。会計へ反映する場合は業務フロー2へ進む。

## 業務フロー2: 消込結果を freee会計 に取引反映する

取引反映は非同期で行われる。取引反映APIの成功応答は受け付けたことだけを表し、反映できたことを表さない。

1. 消込結果を取得し、対象と現在の status を確認する
2. freee会計 に決済の取引が計上されることを説明し、ユーザーの確認を得てから取引反映APIを呼び出す
3. 消込結果を取得し直し、status を確認する
   - posting: 取引反映中。時間をおいて再度確認する
   - posted: 取引反映済み
   - post_failed: 取引反映失敗。`accounting_sync_error_reason_message` をユーザーに示す
4. post_failed の場合は、原因を解消してから再度取引反映する。`accounting_sync_error_reason` が時間をおけば解消する種類の場合は、その旨を伝えて再実行の判断をユーザーに求める

取引反映を受け付けた時点で「取引反映しました」と報告しない。posted を確認できるまでは「受け付けた」「反映中」と伝える。

## 業務フロー3: 取引反映の取消と消込の解除を判定する

ユーザーの「取り消して」「やり直したい」といった表現だけでは、次のどちらを意図しているか確定できない。

- 取引反映の取消: freee会計 に計上した決済の取引を削除し、消込結果は残して status を allocated に戻す
- 消込の解除: 消込結果そのものを取り消し、請求残額と入金残額を消込前に戻す

次の順序で判定する。

1. 消込結果を取得し、status、請求、入金、差額調整の内容を確認する
2. 対象事業所と消込結果の内容をユーザーに示す
3. ユーザーの目的が「会計への計上だけを取り消す」か「消込自体をやり直す」かを確認する
4. 目的と status に応じて、取引反映の取消または消込の解除へ進む

### 取引反映を取り消す場合

1. status が posted であることを確認する。post_failed の場合は取り消すものが無いため、消込自体をやり直すかをユーザーに確認する
2. freee会計 の決済の取引（差額調整の取引を含む）が削除され、請求に対応する取引が未決済または決済中に戻ることを説明し、ユーザーの確認を得る
3. 取引反映の取消APIを呼び出す
4. 消込結果を取得し直し、status が allocated に戻ったことを確認する

結果が分からない場合は、再実行する前に消込結果を取得して status を確認する。

### 消込を解除する場合

消込の解除は元に戻せない。解除した消込結果は取得できなくなり、差額調整も削除される。

1. 解除による影響をユーザーに説明する
   - 請求残額と入金残額が消込前に戻る
   - freee会計 で入金が変更・削除されていた場合、その変更が入金に反映される
   - freee会計 で入金を処理済みにしていた場合、解除後は再度消込できない
2. 対象の消込結果と対象事業所を再提示し、ユーザーから明示的な実行確認を得る
3. 消込の解除APIを呼び出す
4. 請求取得・入金取得で、請求残額と入金残額が戻ったことを確認する

ユーザーの明示的な実行確認なしに解除してはならない。「取り消して」という最初の依頼だけを、元に戻せない操作に対する確認として扱わない。

取引反映済み（posted）の消込結果を解除する場合に、先に取引反映の取消が必要かどうかを推測しない。APIがエラーを返した場合は、その内容をユーザーに示して次の操作を確認する。

当月の充当件数は、消込を解除しても減らない。従量課金を避ける目的での解除は効果がないことを伝える。

## 結果の伝え方

- 消込時は、消込結果ID、消込番号、対象の請求と入金、差額調整、status（allocated）を示す
- 取引反映時は、受け付けたことと、確認できた最新の status を分けて示す
- 取引反映の取消・解除時は、どちらの操作を行ったかと、取得し直して確認した結果を示す
- API呼び出しに成功していない場合や、非同期処理の完了を確認していない場合は、完了したように表現しない

## エラー対応

実行時点の正式OpenAPIを優先する。このレシピとOpenAPIが異なる場合は、OpenAPIに従う。

- 400: フィールド別のエラー情報を確認し、修正が必要な値をユーザーに示す。値を推測して再試行しない
- 401/403: `freee_auth_status` と現在の事業所を確認する
- 404: IDと対象事業所を確認する。解除した消込結果も 404 になる
- 409・422: 返されたメッセージをユーザーに示す。処理中であることが理由の場合は、時間をおいて再実行するかをユーザーに確認する
- 429: 応答の再試行指示に従い、呼び出し回数を抑える

事業所が誤っている場合は、`freee_list_companies` で候補を確認し、ユーザーの意図に合う事業所へ `freee_set_current_company` で切り替えてから再実行する。
